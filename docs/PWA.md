## Service worker rules

- Precaches only public static assets (fonts, icons, manifest, `offline.html`) in a versioned cache `pp-static-<VERSION>`. Bump `VERSION` in `sw.js` to ship changes; old `pp-static-*` caches are deleted on activate.
- Never touches `/api/*`, non-GET, cross-origin requests; nothing authenticated or premium is ever stored. Pages are not cached: navigations are network-first and only a failed navigation shows `offline.html`, which says plainly that most things need a connection.
- Update path: a new worker waits. The page shows a small "A new version is ready" toast with Refresh (posts `SKIP_WAITING`, reloads once on `controllerchange`). Without the click it takes over after all tabs close. First install is silent. Registration happens after `load`, client-only, and is skipped in the Vite dev server.
- `push`: parses the JSON payload (kind, title, body, url, tag) per the V5 contract, shows title and body only (no extra data on the lock screen), `tag` dedupes. `notificationclick`: re-validates `url` (same origin, exact allow-list match, plan id `pl-` + 8 [a-z0-9]), focuses an existing window and navigates, else opens a window; anything else falls back to `/`.

## Launch gate: `PWA_PROMPTS_ENABLED`

`export const PWA_PROMPTS_ENABLED = false` in `src/lib/pwa.ts` (the `pwaInstallPrompts` flag). While false:

- `InstallPrompt` and `InstallCard` render nothing, anywhere. Nothing proactive encourages installing, and no customer-facing page advertises installing, PWA or offline use.
- `/install` still works by URL, is `noindex`, is not in the sitemap and is not linked from the header, footer, FAQ, `/unlock` or home. Its first paragraph says installing is optional and the website works fully in the browser. The only in-app pointer is in My Passport notification settings, which must tell iPhone and iPad customers plainly that reminders need the home-screen app (and that this is not confirmed on every iPhone version).
- With `PWA_ENABLED` false (the current state) the manifest is not linked and no service worker is registered, so nothing is installed or cached. Once `PWA_ENABLED` is true the worker caches only public static assets and never touches `/api/*`.

Flip it to `true` only after the rule in `docs/PWA-DEVICE-TEST.md` ("Install prompts stay hidden until these pass") is satisfied on real devices. Q2 may mirror the value in commercial config; the components read only this constant.

## When the install invitation may appear (flag true)

Only after verified purchase, activation, migration of the free intro progress and saved adventures, and a successful first sync: `useInstallEligible()` is `PWA_PROMPTS_ENABLED && entitlement === "entitled" && sync status === "saved"` (the sync controller says "saved" only after the server confirmed it holds everything this device has). `InstallPrompt` is mounted in the activation/restore success state (`AccessForms.tsx`); `InstallCard` is the quiet card in My Passport for entitled customers. Never during discovery, checkout or free onboarding (the free-flow completion panel in `FreeStarter.tsx` has no install prompt; it has a plain note about where progress lives). Hidden when already standalone; not again for 90 days after "Not now" (`pp.install.dismissedAt`, try/catch). "Install" uses the captured `beforeinstallprompt` where Chromium offers it, else links to `/install`.

## Authentication and storage in the installed app

Source read 2026-11-26: WebKit, "WebKit Features in Safari 17.2" (https://webkit.org/blog/14787/webkit-features-in-safari-17-2/), section "Login cookies": on iOS and iPadOS 17.2 and later, when a person taps Add to Home Screen from Safari, Safari View Controller or another browser, the site's cookies, including login state, are copied into the new web app. "This will only work if the authentication state is stored within cookies. No other kind of local storage is copied over. After a user adds a web app to the Home Screen or Dock, no other website data is shared." Later changes are not synchronized in either direction; the two contexts are separate afterwards. Read from the published page only; not tested on a device (UNVERIFIED on device).

How our architecture lines up:

| Item                                                  | Where it lives                                                                                  | Carried into a new home-screen app (iOS 17.2+)?                                                                                                                          |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Session `pp_session` (signed, opaque customer id)     | Cookie: `Path=/; Max-Age=2592000 (30 days); HttpOnly; Secure; SameSite=Lax`                     | Expected yes (cookie), copied once at install time. Persistent (has `Max-Age`), which is what we need. Not renewed, so a copied cookie keeps the original 30-day expiry. |
| CSRF token                                            | Derived on the server from the session; fetched from `GET /api/session` and held in memory only | Not stored anywhere, so nothing to copy. The installed app fetches a fresh one on launch.                                                                                |
| `pp.acct.v1` ("this browser has an account") flag     | localStorage                                                                                    | No. Absent in the installed app on first launch.                                                                                                                         |
| Progress `pp.save.v1` (free progress, local copy)     | localStorage                                                                                    | No. Starts empty. Free customers' progress does not follow them into the installed app.                                                                                  |
| Plans `pp.plans.v1`, install-dismiss and detect flags | localStorage                                                                                    | No.                                                                                                                                                                      |
| Push subscription, notification permission            | Per-context (service worker and browser)                                                        | No. Must be granted again inside the installed app, by an explicit action.                                                                                               |
| IndexedDB, Cache Storage                              | Not used for customer data                                                                      | Not applicable. We never assume localStorage or IndexedDB transfer.                                                                                                      |
| Premium library                                       | Memory only, fetched with the session                                                           | Fetched on launch if the session is valid.                                                                                                                               |

Consequences and what we built:

1. The client used to learn "I am entitled" only from the `pp.acct.v1` flag, which is not copied, so a valid copied cookie would never be noticed. Fix: in standalone mode (`isStandalone()`), `startEntitlement()` probes `GET /api/session` once per launch even without the flag (`refreshEntitlement({ probe: true })`). A 401 just leaves the app free. The probe is limited to the installed app, so ordinary free browser visitors still make no network call; a free customer who installs makes one anonymous session check per launch.
2. With a valid session: `useEntitlement` becomes `entitled`, the premium library loads, `useSync` starts, and the first sync PULLS the server save (premium access flag, dog profile, owner preferences, saved adventures, favorites, custom collections, completed adventures, memories; stamps and achievements are derived from `done`, so they reappear) and merges it into the empty local store before any push. Scheduled adventures then sync the same way (below).
3. Without a valid session (the cookie was not copied, expired after 30 days, or an older iOS, or Android/desktop where behavior differs and is unverified): the installed app opens at `start_url` `/passport` and, in standalone mode with an empty store and no session, shows a prominent "Bought the Passport already? Restore access" panel (`RestoreAccessCallout`) linking to `/restore-access` (the purchase code, never in a URL). Export/import is not the standard path for paying customers.
4. Free customers: progress stays on the device; no cloud account exists. A home-screen app is a separate storage context, so free progress made in the browser will not be in it. `/install` and the free completion panel say so briefly; export/import is optional.

Not verified: that the cookie is actually copied on real devices, that `Max-Age` cookies survive, Android WebAPK storage sharing, and what happens after 30 days. See `docs/PWA-DEVICE-TEST.md`.

## What is synced to the server for a customer

| Data                                                       | Store                                 | Merge rule                                                                                                       |
| ---------------------------------------------------------- | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Premium access                                             | Customer record `entitlement`         | Server owned; re-verified with the provider.                                                                     |
| Dog profile, owner preferences                             | `Save` (`PUT /api/progress`)          | Last write wins by timestamp, an empty profile has `at: 0` and can never win.                                    |
| Saved, favorites, completed adventures; custom collections | `Save`                                | Timed add/remove sets and collection tombstones (union, newer edit wins); never replace.                         |
| Stamps, achievements, milestones                           | Derived from `done` and the library   | Not stored.                                                                                                      |
| Scheduled adventures (plans)                               | Notification record (`/api/schedule`) | Per id, newer `updatedAt` wins; `done`/`cancelled` are kept as tombstones; stale writes are ignored server side. |

Plans live locally in `pp.plans.v1` (local first) and, for every entitled customer, sync through `/api/schedule` whether or not reminders (push) are on. `syncPlans()` (`src/lib/plans.ts`) pulls, merges, then pushes only plans the server lacks or holds an older copy of; cancel and done are sent as a status change, never a delete; a failed pull pushes nothing. `useSync` runs it after the first progress sync, on focus, when back online and (debounced) after a local plan change. The server `PUT /api/schedule/<id>` takes the client's `updatedAt` (clamped to five minutes ahead of server time) and, when the stored plan is newer, returns the stored plan with `stale: true` instead of overwriting it.

## Empty-state overwrite protection (audit, 2026-11-26)

- Server: `PUT /api/progress`, activate and restore all go through `mergeProgress`/`merge`, which only unions sets, keeps the later timestamp per field and takes the larger tombstone; the client cannot set `rev`. An empty save is a no-op (`changed: false`, no revision bump). There is no endpoint that replaces a save.
- Client: `SyncController.start()` pulls and merges first; a local edit during the pull waits for it; the first push happens only if the merged local copy differs from the server. Plans: pull, merge, then push (above).
- Tests: `src/test/pwa-empty-state.test.ts` (server and client), `src/test/passport-sync.test.ts`, `src/test/server-passport.test.ts`.
- Known limit, not changed: the dog profile and owner preferences are whole-object last-write-wins. If someone deliberately edits the profile on a fresh device before signing in, that newer edit wins over an older remote profile. That is a real edit, not an empty state.
