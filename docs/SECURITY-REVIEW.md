# Security review (pre-launch, code review plus unit tests)

Scope: the Adventure Passport server (`src/server/passport/**`, `netlify/functions/**`), the client code that touches photos and the network, the service worker, repository hygiene, and the response headers in `netlify.toml` (read only).

**What this is.** A read-through of the actual code plus executed unit tests against the real request handler with an in-memory store and a fake provider. **What this is not.** No penetration test, no scan of a deployed site, no test against real Netlify Blobs, real Gumroad, or real push services. Anything that depends on those is marked "unverified" and appears in the Cowork tasks it points to at the end.

Executed tests added: `src/test/security-api.test.ts` and `src/test/security-static.test.ts`. They run with the normal `vitest` suite. They sit beside the existing `server-passport.test.ts`, `push-api.test.ts`, `previews-server.test.ts` and `security-headers.test.ts`.

Result key: OK = read and (where noted) tested, no defect. Defect = needs action. Unverified = cannot be proven from the repo.

## Launch-blocking defects

None found in the code. One owner decision is outstanding and is a risk to the paywall, not a code defect:

- **P1 (closed in the tree): premium text is not tracked.** `content/premium/*.json` is git-ignored and guarded by a test; the protected package is kept outside the repository (location held by the owner), and `scripts/sanitize-check.mjs` scans tracked files for private markers and secret patterns.

## Preview isolation (verified 2026-11-27, source and tests)

1. Stores: `storeEnv` is "production" only for the `production` deploy context; branch deploys, deploy previews, dev and unknown contexts open `customers-preview` and `premium-preview` (`preview-isolation.test.ts` drives the real `handleNetlify` with a recording blobs fake; `netlify-env.test.ts` pins the names).
2. Test entitlements: `TestProvider` throws in production, unknown and empty contexts, and needs `PP_ALLOW_TEST_PROVIDER` exactly "1"; the flag set by mistake in production grants nothing (503, no cookie).
3. Preview defaults (public throwaway secrets plus the test flag) apply only to `branch-deploy` and `deploy-preview`, never to production, dev or unknown.
4. Missing production configuration (no `SESSION_SECRET`/`PP_DATA_KEY`, or no `GUMROAD_PRODUCT_ID`) returns a safe 503 from session and activation, never a grant and never a fallback to preview defaults.
5. Premium endpoints: no session means 401/503 with no premium text in every context; a preview serves only what its own `premium-preview` store holds (empty or synthetic unless the owner imports content).
6. The real premium package is not bundled in `dist` or the functions bundle (leak scan above; `premium-package.test.ts`, `security-static.test.ts`).
7. Analytics never load on non-production hosts, even after consent (`consent.test.tsx`).
8. Non-production hosts send `X-Robots-Tag: noindex, nofollow` on HTML (`security-headers.test.ts`). Still unverified: real deployed headers (B5) and Netlify context values in a live preview (B6).

## Small defects and what was done

No code was changed in `src/server/**` or `netlify/functions/**`: nothing found there was both clearly wrong and clearly safe to change without product decisions. Candidates left as is:

1. Sign-out route (item 4): resolved after this review; sign-out is per device only (stateless cookies). A per-customer session epoch for "sign out everywhere" is a possible later feature, not built.
2. A missing client IP puts everyone in one rate-limit bucket (item 10). Netlify supplies the header; no change.
3. CSRF token compared with `!==` (item 5): negligible.

## For worker N (netlify.toml, not edited by S)

- Add `X-Content-Type-Options = "nosniff"` to the `/*` header block (safe). HTML pages need it in `src/lib/security-headers.ts` as well; that file belongs to another worker.
- Consider a Content-Security-Policy in report-only mode first; inline scripts in the root document would need a hash or nonce. Not safe to ship enforcing without a browser test.
- Decide on a frame policy knowingly (currently none, so the site can be framed; this matters for click-jacking of the unlock page).
- Confirm HSTS on the deployed domain.
